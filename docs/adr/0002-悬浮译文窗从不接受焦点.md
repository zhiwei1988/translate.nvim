# 悬浮译文窗从不接受焦点,长译文靠临时劫持源 buffer 的滚动键就地翻阅

悬浮译文窗定为**不抢焦点**,且光标离开段落即关窗——这两条合起来让"进浮窗滚动"的方案自我摧毁:光标一进浮窗就不在段落区间内,窗口当场关闭。而列表整体送翻、表格照译加上术语双写,让译文溢出高度上限成为**常态**而非边缘情况,全文必须可达。我们的选择是**让光标永远留在原文里**:浮窗内容溢出时,插件在**源 buffer** 上临时挂 `<C-d>` / `<C-u>` 的 buffer-local 映射,按键滚动浮窗视口而光标一步不动,浮窗关闭即解绑。

## 为什么劫持用户 buffer 的按键是可接受的

在「浮窗开着 + 光标在段落内」这个状态下,`<C-d>` 的原语义**本来就等价于关掉浮窗**——它滚动主窗口、带走光标、离开段落、触发关窗。改成"滚动浮窗"没有夺走任何有价值的东西。

这个论证有边界,它划定了实现必须遵守的三条:

- **只对带走光标的键成立。** `<C-e>` / `<C-y>` 滚动主窗口却不移动光标,浮窗不会关——它们原本能微调视口并保持浮窗开着,劫持是**有损**的,因此明确不碰。
- **只在真的溢出时成立。** 未溢出时用户按 `<C-d>` 的意图毫不模糊(滚主窗、顺便关掉看完的浮窗),此时劫持只会给他一个死键。所以映射**只在内容超出窗口高度时才挂**,这是个跟着流式增长动态变化的状态。
- **`q` 不在其列。** normal 模式下 `q` 是录制宏的前缀,劫持后 `qa` 会变成"关窗 + 进入插入模式",在用户的文档里开始打字。手动关窗只保留 `<Esc>`。

## 备选方案与否决理由

- **进入浮窗滚动**(生态里最常见的做法)——要么破坏"不抢焦点"基线,要么得给关闭逻辑开"光标在浮窗里不算离开"的豁免口,随后还要处理"怎么回到原文""浮窗内误按会不会关窗""浮窗键位与用户全局映射如何共存"。这是把一台干净的状态机拆掉重装,换来的只是省掉几个临时映射。
- **截断 + 提示**——token 已经花掉、完整译文已写进持久缓存,却只让用户看前半截,是最糟的一种浪费;而术语双写让截断会天天发生。
- **溢出时升级成居中大浮窗**——不是坏主意,但第二级形态要另定尺寸、焦点、关闭以及与流式和缓存的关系,是另一整套决策。原地滚动已让全文可达,升级视图可作为将来的纯增量补充,不破坏此处任何结论。
- **流式期间视口跟随最新内容**——阅读从第一行开始,tail-follow 会让第一行几秒钟就滚出视野,用户根本没机会读。钉在开头还顺带消掉了"边滚边长"的竞态:用户读前 20 行的工夫,剩下的已在后台生成完。

## 后果

- **浮窗内的插件键位数量为零。**「用户命令面与运行时切换」把"浮窗内 buffer-local keymap"划归插件,实际落点却是**源 buffer 上的临时映射**。浮窗仍要有固定 `filetype`(`translate-float`)供用户挂自己的 autocmd 与高亮。
- **绑定与解绑成为窗口生命周期的一部分**,且随流式内容增长动态发生——任何"浮窗已关但映射还在"的路径都会在用户自己的 buffer 里留下幽灵键位,这条必须有测试覆盖。
- 滚动位置指示走浮窗 `footer`(`↓ 还有 N 行`),标题栏留给 `provider · model` 与 `⚡` / `⚠`。

完整的决策讨论见 [长译文超出浮窗高度上限时如何查看](https://github.com/zhiwei1988/translate.nvim/issues/13)。

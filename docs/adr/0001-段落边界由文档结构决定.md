# 段落边界由文档结构决定,缓存键策略随块类型分叉

悬浮翻译的基本单位最初被定为"空行分隔的连续文本块",但 Markdown 里空行并不可靠地对应语义边界——松散列表的每一项之间就有空行,而它们属于同一个列表。我们改为**由文档结构决定段落边界**:一个散文块、一整个列表(含全部嵌套项)、一张表格、一个引用块、一个标题各自成段;代码块、HTML 块、分隔线是**不可翻译块**,永不单独送翻。这条路之所以走得通,是因为 Markdown 的 treesitter parser 是 Neovim 自带的(自 0.10 起编译进二进制),结构感知不引入任何运行时依赖;非 Markdown 文件则退化为纯空行扫描。

## 备选方案与否决理由

- **纯空行扫描,不做结构感知**——最简单,但松散列表会被切碎,而紧凑列表不会,同一份文档里同类内容行为不一致。
- **列表按 item 切,或长列表降级按 item 切**——"整个列表 = 一段"是刻意选的:LLM 拿到全部项才能正确处理项间省略的主语与并列关系。降级方案更糟,它让用户无法预知哪个列表会踩线,把已经消灭的不一致从后门放回来。长列表翻得慢是**成本**问题,不是正确性问题,不该藏在段落检测里解决。
- **缓存键一律用规范化原文**——规范化(折叠空白、行间单空格连接)的唯一收益是"同一段文字换个折行方式仍能命中缓存",而软折行只存在于散文。列表和表格里每个行边界都是作者手写下的结构,规范化零收益还撞键:`- a` / `- b` 两行规范化后与单行的 `- a - b`(一个列表项)同键,译文却不同。
- **送翻前剥离 Markdown 标记**——不归路。译文流式返回后无法把标记还原到正确位置,浮窗里的加粗、链接文字、行内代码会全部丢失;而"剥离"本身就是在手写一个 Markdown 解析器。
- **按 parser 可用性而非 `filetype` 决定是否走结构路径**——会把 Python 文件按 Markdown 解析,`#` 开头的注释整片变成"标题"。

## 后果

- **缓存键策略按块类型分叉**:散文段落用规范化原文,列表/表格/任何含不可翻译块的内容用原始字节。因此段落检测的输出必须携带块类型,缓存层不能只拿到一段裸文本。
- **system prompt 承担了一项正确性义务**。`list_item` 可以包含围栏代码块,而列表整体送翻,所以"代码不被翻译"在这种情形下**只由 prompt 保障**,没有代码层面的兜底。这条必须有测试覆盖。
- **浮窗溢出从边缘情况变成常态**。列表不设长度上限、表格整张照译,译文经常超过既定的半屏高度上限。溢出后的行为是一个独立的待决问题。
- 纯文本文件的体验不受影响:fallback 路径就是光标周围的连续非空行,与最初的定义一致。

完整的决策讨论见 [段落检测与选区语义](https://github.com/zhiwei1988/translate.nvim/issues/3)。
